# Security Design

## 1. Instance Authentication
The primary security challenge is verifying that usage reports come from a legitimate deployed instance.

### 1.1 Credential Strategy
- **Shared Secret (API Key)**:
  - Generated by Central System at registration.
  - Format: `sk-inst-[8-char-prefix]-[32-char-secret]`
  - Stored hashed (`argon2id`) in Central DB.
  - Stored encrypted (AES-256) in Instance local DB (`localDb.js`).

### 1.2 Handshake & Rotation
### 1.2 Handshake & Identity (Wallet Auth)
1.  **Identity Proof**:
    -   Router generates a random `MachineID` (UUID).
    -   Owner signs a message: `Register FlexIA Router\nMachine ID: [UUID]\nTimestamp: [Now]` using their Web3 Wallet.
    -   Router sends Signature + Public Address to `/register`.
2.  **Verification**:
    -   Central System recovers address from signature.
    -   Verifies address matches the claimed owner.
    -   Issues a long-lived **Instance API Key** for future API calls.
2. **Key Rotation**:
   - Instance automatically requests new key every 30 days.
   - Old key remains valid for overlap period (24h) to prevent outages.

## 2. API Security

### 2.1 Inbound Requests (SaaS User -> Router)
- **Validation**: Router must validate the `Authorization: Bearer sk-...` header.
- **Mechanism**:
  - **Local Mode**: Checks against local `apiKeys` in `localDb.js`.
  - **SaaS Mode**: Validates against a synchronized list of allowed keys or calls Central System (cached). *Recommendation: Sync valid key hashes to instance for low-latency validation.*

### 2.2 Outbound Requests (Router -> Central)
- **Transport Security**: TLS 1.3 enforced.
- **Headers**:
  - `X-Instance-ID`: UUID
  - `Authorization`: `Bearer sk-inst-...`
  - `X-Request-Signature`: HMAC-SHA256 of body (optional, for non-repudiation).

## 3. Data Protection

### 3.1 Data Minimization
- **Body Content**: The actual prompts and completions (PII-heavy) are **NEVER** sent to the Central System.
- **Aggregation**: Only token counts, model names, and cost are transmitted.
- **Masking**: End-user IDs are hashed if they contain PII (e.g., email addresses).

### 3.2 Database Security
- **Encryption at Rest**: Sensitive fields (API Key Secrets) are encrypted.
- **RLS (Row Level Security)**: Supabase RLS policies enforced so instances can only insert their own usage data (if they accessed DB directly, though API is preferred).

## 4. Operational Security

### 4.1 Rate Limiting at Edge
The Router Instance protects itself and the providers:
- **Token Bucket**: Limit RPM (Requests Per Minute) per User ID.
- **Budget Limits**: Soft/Hard caps on daily spend per Tenant.

### 4.2 Audit Logging
- **Central System**: Logs all Registration, Key Rotation, and Config Change events.
- **Router Instance**: Logs access attempts to local `logs.txt` (and optionally streams errors to Central).
